== Purpose of the Plugin

`Octopus Build Integration Gradle Plugin` adds the ability to export the list of components your project depends on into a file,
with only direct (non-transitive) dependencies being considered.

The list is formed based on:

* explicitly defined components;
* Gradle dependencies.

== Applying the Plugin

To use the `Octopus Build Integration Gradle Plugin` in a project, follow these steps:

1. Define the plugin version in `gradle.properties` using the parameter `octopus-build-integration.version`.
2. Apply the plugin in `settings.gradle(.kts)`, as well as in the `build.gradle(.kts)` file of the required module
3. Ensure the `exportDependencies` task runs automatically by adding it
as a dependency of a task that always executes (for example, `assemble`).

[IMPORTANT]
====
It is very important to use the **exact version parameter name**:
`octopus-build-integration.version`.

This allows TeamCity to automatically supply the current plugin version
for each build.
====

=== Kotlin DSL

.settings.gradle.kts
[source,kotlin]
----
pluginManagement {
    plugins {
        id("org.octopusden.octopus-build-integration") version extra["octopus-build-integration.version"] as String
    }
}
----

.build.gradle.kts
[source,kotlin]
----
plugins {
    id("org.octopusden.octopus-build-integration")
}

tasks.named("assemble") {
    dependsOn("exportDependencies")
}
----

=== Groovy DSL

.settings.gradle
[source,groovy]
----
pluginManagement {
    plugins {
        id 'org.octopusden.octopus-build-integration' version (settings.ext['octopus-build-integration.version'] as String)
    }
}
----

.build.gradle
[source,groovy]
----
plugins {
    id 'org.octopusden.octopus-build-integration'
}

tasks.named("assemble").configure {
    dependsOn "exportDependencies"
}
----

== Plugin Configuration
=== DSL Reference
[cols="3,6,3,3", options="header"]
|===
| DSL Element
| Description
| Default
| Override via `-P`

| `releaseDependencies { component ... }`
| Explicitly declared components (see the forms below).
| -
| -

| `scan.enabled`
| Enables or disables Gradle dependency scanning. Declaring a `scan { }` block enables scanning implicitly; this flag (or the `-P` override) can still force it off.
| false (true once a `scan { }` block is declared)
| `-Pdependencies.scan.enabled`

| `scan.componentsRegistryUrl`
| URL of the Components Registry service. Used only when scanning is enabled.
| -
| env `COMPONENT_REGISTRY_SERVICE_URL`

| `scan.projects`
| Regular expression used to filter projects by their path
| .+
| `-Pdependencies.scan.projects`

| `scan.configurations`
| Regular expression used to select Gradle configurations from which dependencies are extracted.
| runtime.+
| `-Pdependencies.scan.configurations`

| `outputFile`
| Name of the file to which the plugin will write the resulting dependency list.
| components-dependencies.json
| `-Pdependencies.outputFile`

|===

[NOTE]
====
The Components Registry URL is resolved from the `COMPONENT_REGISTRY_SERVICE_URL`
**environment variable** (consistent with `octopus-rm-gradle-plugin`), falling back to
`scan.componentsRegistryUrl` from the DSL. The remaining settings are overridable via Gradle
project properties (`-Pdependencies.*`). These override keys are independent of the
`releaseManagement` / `releaseDependencies` / `scan` DSL block names.
====

=== Configuring

All configuration lives under the `releaseManagement` extension. Explicit components are
declared in a `releaseDependencies { }` block and scanning is configured in a sibling
`scan { }` block.

If you want to explicitly add a component, it can be done as follows (no import required):

.build.gradle.kts
[source,kotlin]
----
releaseManagement {
    releaseDependencies {
        component("component_a", "1.0.0")
        component("component_b:1.1.0")
    }
}
----

.build.gradle
[source,groovy]
----
releaseManagement {
    releaseDependencies {
        component name: 'component_a', version: '1.0.0'
        component 'component_b:1.1.0'
    }
}
----

A component can be declared in either form:

* `component name: "<name>", version: "<version>"` (Groovy named arguments);
* `component "<name>:<version>"` (single string);
* `component("<name>", "<version>")` (convenient for the Kotlin DSL).

If you need to include Gradle dependencies, you can configure scanning as follows. Declaring
a `scan { }` block enables scanning automatically — `scan.componentsRegistryUrl` must be
provided (usually via the `-P` override):

.build.gradle.kts
[source,kotlin]
----
releaseManagement {
    scan {
        // only root project ":"
        projects.set("^:$")

        // only subproject ":service-a"
        projects.set(".*:service-a")

        // subprojects ":service-a" and ":service-b"
        projects.set(".*:(service-a|service-b)")

        // exclude subprojects with names starting with "legacy-"
        projects.set("^(?!.*:legacy-).+")
    }
}
----

.build.gradle
[source,groovy]
----
releaseManagement {
    scan {
        // only root project ":"
        projects.set('^:$')

        // only subproject ":service-a"
        projects.set('.*:service-a')

        // subprojects ":service-a" and ":service-b"
        projects.set('.*:(service-a|service-b)')

         // exclude subprojects with names starting with "legacy-"
        projects.set('^(?!.*:legacy-).+')
    }
}
----

If you need to filter Gradle configurations from which dependencies are collected, you can configure them as follows:

.build.gradle.kts
[source,kotlin]
----
releaseManagement {
    scan {
        // include runtimeClasspath and compileClasspath dependencies
        configurations.set("(runtimeClasspath|compileClasspath)")

        // exclude test dependencies
        configurations.set("^(?!test).*")
    }
}
----

.build.gradle
[source,groovy]
----
releaseManagement {
    scan {
        // include runtimeClasspath and compileClasspath dependencies
        configurations.set('(runtimeClasspath|compileClasspath)')

        // exclude test dependencies
        configurations.set('^(?!test).*')
    }
}
----

== Migrating from octopus-rm-gradle-plugin

This plugin reuses the `releaseManagement { }` extension name and the explicit
`releaseDependencies { component ... }` syntax from `octopus-rm-gradle-plugin`, so projects
that only declared explicit components migrate with **no configuration changes** — just
replace the plugin.

Projects that scanned dependencies need to rewrite that part, because the scanning model
changed: instead of filtering resolved artifacts by `group`/`module`, scanning now selects
which subprojects (`scan.projects`) and which Gradle configurations (`scan.configurations`)
to read.

[cols="5,5,3", options="header"]
|===
| octopus-rm-gradle-plugin | This plugin | Notes

| `component name: "x", version: "y"`
| `component name: "x", version: "y"`
| Identical.

| `component "x:y"`
| `component "x:y"`
| Identical.

| `releaseDependencies { fromDependencies { ... } }`
| `scan { projects.set(...); configurations.set(...) }` (sibling of `releaseDependencies`)
| Different filtering model; the `scan` block lives directly under `releaseManagement`.

| `fromDependencies { include module: "...", group: "..." }`
| `scan { projects.set(...); configurations.set(...) }`
| Rewrite to project/configuration regexes. Only artifacts whose group is registered in the Components Registry are kept.

| `fromDependencies { exclude ... }`
| —
| No direct equivalent. Narrow the `scan` regexes instead.

| presence of `fromDependencies` turned scanning on
| presence of a `scan { }` block turns scanning on
| Same ergonomics.

|===
